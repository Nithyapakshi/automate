Three-bucket agent autonomy ladder: every recurring agent task is sorted by how bad it is if the agent gets it wrong

Date
2026-10-19
Source
Allie K. Miller on LinkedIn (third-party mirror)
What changed
Jarvis, hub and BookLog agent tasks get an explicit bucket. Bucket 1: easy to undo and invisible, the agent runs it alone. Bucket 2: easy to undo but in his name, the agent drafts and waits for his yes. Bucket 3: hard to undo, straight to him (money, legal, personal contacts). New automations start in bucket 2 and graduate to bucket 1 after 5 consecutive accepted drafts.
Status
Adopted
Project
Jarvis, hub and BookLog agent tasks
What we did
Working practice, no code. The bucket ladder now governs how Jarvis, hub and BookLog agent tasks run and when they ask.
How to use it
Approved by the user 19 Oct 2026 (7:49am). Applied to new automations from this date; graduation counts start per task.

Critic pass before publish: a fresh critic agent reviews live-facing changes before they ship

Date
2026-10-18
Source
James Raybould (Fun Friday experiment transcript)
What changed
BookLog and hub changes that touch live users are reviewed by a separate fresh critic agent (no memory of the build) against standing rules and real data before they come to the user; findings are fixed first, then presented with the Testing / Risk / Revert note.
Status
Adopted
Project
BookLog and hub changes touching live users

Working practice, no code. Before a live-facing BookLog or hub change is presented, a separate critic agent without build context reviews the result against standing rules and real data. Approved by the user 18 Oct 2026 (8:24am). The first use will be flagged for the log; not applied retroactively to same-day publishes (hub gens 123-124).

Our mapping - separate synthesis

How to use it

Deep pick · It answers a concrete builder question: when should a background AI job use an always-on worker rather than cron or a request handler? The primary guide gives implementation steps, limits and a bounded test path.

The method: Use Daemons for a continuous pull loop. Keep scheduled tasks on Cron, HTTP work on Functions/Services, durable multi-step logic on Workflows, and untrusted code on Sandbox. Package the worker in a Dockerfile/Containerfile, declare its regional instance count, then deploy to production. This is a reading pack, not a deployment instruction for an existing app.

The numbers that change the decision: The guide gives a 10-second shutdown grace period and no autoscaling. Jobs must be retry-safe and acknowledged only after success. Hobby has 10vCPU-hours per month shared across the team's projects: one 1-vCPU instance running continuously uses that allowance in about 10hours, not a month. Account eligibility and remaining allowance are not verified.

A sensible first test: After specific approval and a verified zero-cost path, use a disposable sample worker with synthetic jobs. Check restart/redelivery, duplicate protection and graceful shutdown. Avoid real user data and production workloads. This is our suggested test, not something already run.

Watch-outs: Preview deployments do not start Daemons; vercel dev does not run them either. Test locally with Docker. The launch example uses replicas while the current guide specifies instances and rejects other fields. Confirm the current schema before implementing; do not copy the launch example blindly.
